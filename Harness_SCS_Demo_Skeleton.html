2b. CI/CD Toolchain Compromise — tj-actions/changed-files (CVE-2025-30066) (~5 min)

Differentiation Point: This demonstrates a CI/CD pipeline attack — fundamentally different from application dependency vulnerabilities. Most competitors have zero visibility into this attack surface. RSPM is the Harness answer.

The Attack: What Happened

  • In March 2025, attackers compromised the tj-actions/changed-files GitHub Action (one of the most popular on the marketplace)
  • They rewrote the v35 Git tag to point to malicious code that exfiltrated all CI/CD secrets (GITHUB_TOKEN, cloud keys, registry credentials) to workflow logs
  • Over 23,000 repositories were affected — any repo using @v35 (a mutable tag) automatically pulled the compromised version
  • Root cause: GitHub Actions mutable tags can be force-pushed to any commit at any time

Live Demo: RSPM Detection

  • Show the repo's .github/workflows/ci.yml workflow file referencing tj-actions/changed-files@v35
  • Show RSPM scan results: Compromised CI/CD action detected — CVE-2025-30066, Critical severity
  • Map finding to OWASP CI/CD-SEC-3 (Dependency Chain Abuse) and CIS Supply Chain Benchmark controls
  • Show blast radius: GITHUB_TOKEN, Docker registry credentials, cloud provider keys, Cosign signing key passphrase — all at risk

Remediation: Pin to Immutable SHA

  • Show the remediated workflow: all actions pinned to immutable commit SHAs instead of mutable tags
  • Before: uses: tj-actions/changed-files@v35 (attacker can rewrite tag)
  • After: uses: tj-actions/changed-files@6b2903bd...c9 (cryptographic hash — cannot be changed)
  • OPA policy blocks any build referencing the compromised tag via blocked_cicd_actions in the block policy
  • Remediation Tracker entry: pin to SHA, rotate all potentially exposed secrets, audit every workflow in the org
Talk Track: "A single compromised action gave attackers the keys to the kingdom — every secret in your CI environment. RSPM caught it. OPA blocked it. And the Remediation Tracker manages the full response lifecycle. No other supply chain tool covers this attack surface."

2c. xz-utils Backdoor — CVE-2024-3094 (~4 min)

Differentiation Point: This is the most sophisticated supply chain attack in history — a 2-year social engineering campaign. It demonstrates why SBOM + policy enforcement is essential even when provenance appears "verified."

The Attack

  • A malicious actor ("Jia Tan") spent 2+ years gaining trust as an xz-utils maintainer
  • Injected a backdoor via modified build scripts and malicious test files into versions 5.6.0 and 5.6.1
  • The backdoor hijacked OpenSSH authentication via glibc IFUNC, enabling unauthorized remote SSH access — CVSS 10.0
  • Affected distros: Fedora 41/Rawhide, Debian testing/unstable, Kali Linux, openSUSE, Alpine edge

Harness SCS Detection & Response

  • SBOM scanning identifies all containers with xz-utils 5.6.0/5.6.1 via artifact view
  • OPA policy blocks vulnerable versions: deny-vulnerable-versions.rego blocks xz-utils 5.6.0 and 5.6.1
  • Remediation Tracker shows blast radius — which base images (alpine, debian, fedora) bundle xz-utils
  • Remediation: downgrade to 5.4.x via distribution package managers
Talk Track: "This attacker didn't hack an account — they became a trusted maintainer over 2 years. Provenance showed 'verified' because the maintainer was legitimate. Only SBOM-based version blocking caught the backdoor. This is why Harness SCS enforces policies on component metadata, not just trust."

2d. NPM Mass Account Takeover — Sep 2025 (~3 min)

10. Technical Q&A Anchors & Recommended Next Steps (~3 min)

Anticipated Technical Questions

  • "We already use Snyk / Black Duck for SCA — why do we need SCS?" — SCS goes beyond OSS; RSPM, SLSA L3, and Remediation Tracker with blast-radius mapping are unavailable in those tools
  • "How do we handle our existing SBOMs from Syft/Grype?" — SCS supports SBOM ingestion; bring your own SBOM and still get policy enforcement, scoring, and drift detection
  • "Is SLSA Level 3 really achievable without a massive lift?" — With Harness Cloud builds, yes — infrastructure isolation is built in, no custom setup needed
  • "What about compromised CI/CD actions like tj-actions?" — RSPM scans workflow files for known-compromised actions (CVE-2025-30066) and flags mutable tag references. OPA policies can block builds referencing compromised actions. Best practice: pin all actions to immutable commit SHAs
  • "What about backdoors like xz-utils?" — CVE-2024-3094 showed that even trusted maintainers can be compromised. SBOM-based version blocking catches backdoored versions (5.6.0/5.6.1) regardless of provenance status. Remediation Tracker maps which base images are affected
  • "How do you handle mass NPM compromises like the chalk/debug takeover?" — OSS Search identifies compromised packages across all repos in seconds. OPA policies block by version for account takeover scenarios. AppSec Agent can auto-generate block policies. Remediation Tracker enforces credential rotation SLAs
  • "What about air-gapped environments?" — Most features work; RSPM is the main exception
  • "How does this help with EO 14028 / FedRAMP compliance?" — SBOM generation + audit logs satisfy EO requirements; SLSA provenance provides the build traceability mandated by NIST SSDF
